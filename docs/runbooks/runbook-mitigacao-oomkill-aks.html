Diagnóstico e Mitigação de OOMKill (Exit Code 137) no AKS

Procedimento passo a passo para triagem imediata, coleta de evidências de consumo de memória e mitigação segura de containers encerrados pelo Linux Kernel OOM Killer em clusters produtivos como aks-split-bra-prd.

Sinal de Alerta OOMKilled / ExitCode 137
Clusters Alvo aks-split-bra-prd / aks-core-*
Observabilidade Dynatrace Davis AI & Kube-Events
Validação Pós-Ação Zero Restarts por 30 min
PASSO 01

Confirmar Eventos de OOMKill e Identificar Pods Afetados

Conecte-se ao cluster AKS correspondente e inspecione os pods com reinicializações recentes e o motivo de término OOMKilled no estado anterior do container:

# 1. Selecionar contexto do cluster produtivo
kubectl config use-context aks-split-bra-prd

# 2. Listar pods com restarts e verificar lastState.terminated.reason
kubectl get pods -n split-prd -o custom-columns=\
"NAME:.metadata.name,RESTARTS:.status.containerStatuses[*].restartCount,REASON:.status.containerStatuses[*].lastState.terminated.reason,EXIT_CODE:.status.containerStatuses[*].lastState.terminated.exitCode"

# 3. Inspecionar eventos de kernel/cgroup no namespace
kubectl get events -n split-prd --sort-by='.lastTimestamp' | grep -iE "OOM|Killing|Evicted"
PASSO 02

Coletar Logs do Container Anterior e Uso Atual (Working Set)

Antes de aplicar qualquer alteração nos recursos, salve os últimos logs da instância encerrada para análise de causa raiz (ex: spike de payload ou memory leak):

# Extrair as últimas 250 linhas do container que sofreu crash
kubectl logs <nome-do-pod> -n split-prd --previous --tail=250 > /tmp/oom-crash-logs.txt

# Verificar consumo em tempo real comparado aos limits configurados
kubectl top pods -n split-prd --containers
kubectl describe deployment split-worker-settlement -n split-prd | grep -A 6 -E "Limits|Requests"
PASSO 03

Mitigação Emergencial (Right-Sizing de Memória + Runtime Flags)

Caso o tráfego produtivo esteja impactado e o node pool possua folga de memória, aplique o patch emergencial elevando o memory limit em 30–50% e abra PR imediato no repositório GitOps para evitar drift:

# Aplicar patch emergencial de memória no Deployment
kubectl set resources deployment/split-worker-settlement -n split-prd \
  --requests=cpu=600m,memory=1024Mi \
  --limits=cpu=2000m,memory=1536Mi

# Acompanhar rollout seguro sem indisponibilidade
kubectl rollout status deployment/split-worker-settlement -n split-prd --timeout=180s
